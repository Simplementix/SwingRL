# Phase 19.2 — Testing Foundation and Database Isolation

**Status:** Approved design, ready for implementation planning
**Author:** Brainstormed with Claude Opus 4.7
**Date:** 2026-05-19
**Supersedes the unblocking work for:** Phase 19.1 PR (paused until 19.2 complete)

---

## Why this exists

Production data on the homelab `pg16` Postgres instance has been destroyed multiple times by test fixtures issuing `DROP`, `TRUNCATE`, or `DELETE` statements. The current safeguard is a `pytest_configure` guard in `tests/conftest.py` that refuses to run if `DATABASE_URL` doesn't name a `*_test` database. This is necessary but insufficient — it is the same class of single-layer defence that failed at Travis CI in March 2018, when a stray `DATABASE_URL=<prod>` in a developer's shell led to Database Cleaner truncating the production database. Travis's post-mortem ranked the spec-helper guard as layer two; layer one was server-side revocation of the destructive privilege from the application role.

We currently have only the weakest layer. A misconfigured environment variable on any machine that can reach `pg16` can still destroy production data. Today's CI failure (50 tests, mostly inter-test state pollution) emerged because the conftest guard correctly routed tests to `swingrl_test` on the shared `pg16` process, but the tests had no isolation from each other or from the prod cluster.

## Goal

Make it architecturally impossible for tests to harm production data, while making the test suite faster, more honest about what it is testing, and structurally easier to maintain.

## Non-goals

- Adopting SQLAlchemy. The codebase uses raw psycopg throughout; introducing an ORM is a separate decision with a much larger blast radius.
- Adopting SQLite as a Postgres substitute. SwingRL depends on Postgres-specific features (`ON CONFLICT`, JSONB, CTEs, sequences, identity columns); faking these with SQLite is documented industry anti-pattern (see Neon's "Dangers of Testing in SQLite as a Postgres User").
- Rewriting domain logic in `agents/`, `training/`, or `scheduler/` beyond the I/O boundary. Repositories replace direct DB calls only.
- New business features. Phase 19.1 work resumes at phase 19.2.6 and is not modified by this milestone.

## Architecture: defence in depth (four layers, all mandatory)

| Layer | Mechanism | What it stops |
|---|---|---|
| L1 — Physical isolation | A separate `pg-test` Postgres process in `docker-compose-dev.yml`, with its own volume, port, and network. Tests connect there; prod `pg16` is on a different process entirely. | Wrong-cluster / shared-process risk. A test cannot connect to prod by misconfiguration because it would have to know prod's address. |
| L2 — Server-side authorisation | On prod `pg16`: revoke `TRUNCATE`, `DELETE`, `DROP` from the application `swingrl` role; introduce a `swingrl_admin` role that owns the schema and runs migrations. `pg_hba.conf` restricts the prod `swingrl` database to connections from the prod app container subnet. | Even a hostile or buggy test holding production credentials cannot destroy data. Even from inside the prod container, the application role lacks the privilege. |
| L3 — Code-level isolation | All 36 modules touching the database are refactored behind `typing.Protocol` repositories. Each repository has a `Pg<Name>Repository` (raw psycopg, lifts current SQL verbatim) and a `Fake<Name>Repository` (in-memory dict). Business modules accept repository instances by argument; they do not import psycopg. | Most tests stop needing a database at all. Tests become deterministic, fast, hermetic, and obviously safe. |
| L4 — Per-test rollback | A custom psycopg fixture (autouse, function-scoped) wraps each integration test in a transaction with `SAVEPOINT` semantics and rolls back at teardown. | Inter-test state pollution, which is the cause of today's 50 failures. |

All four layers ship in this milestone. None substitutes for any other.

## Repository pattern contract

```python
# src/swingrl/<area>/ports.py
from typing import Protocol
from swingrl.domain.models import Position  # Pydantic models, one per aggregate

class PositionRepository(Protocol):
    def get(self, symbol: str, env: str) -> Position | None: ...
    def list_for_env(self, env: str) -> list[Position]: ...
    def upsert(self, position: Position) -> None: ...
    def delete(self, symbol: str, env: str) -> None: ...

# src/swingrl/<area>/adapters/postgres.py
class PgPositionRepository:
    def __init__(self, conn: psycopg.Connection): ...
    # methods execute the same raw SQL we have today

# src/swingrl/<area>/adapters/in_memory.py
class FakePositionRepository:
    def __init__(self, seed: list[Position] | None = None):
        self._store: dict[tuple[str, str], Position] = ...
    # methods manipulate the dict
```

**Wiring rule:** business modules take the specific repositories they need as constructor arguments (or function arguments for module-level functions). The historical pattern of taking `db: DatabaseManager` is replaced. `DatabaseManager` continues to exist as the connection-pool wrapper that PgRepository implementations are built upon; it is itself wrapped by repositories rather than passed around.

**Return types:** Pydantic models for aggregates with mutation semantics (positions, trades, halt state). Bulk-data reads (OHLCV ranges, feature matrices) return DataFrames — forcing model construction on hot paths is an unacceptable performance cost.

**Import discipline:** Only files under `*/adapters/postgres.py` may import `psycopg`. CI enforces this with `grep` (no `import psycopg` outside adapters). The rule lands in CLAUDE.md alongside the existing critical rules.

## Documentation as integral deliverable

Every code-change commit that touches a documented subsystem updates the corresponding doc in the same commit. This is the existing `feedback_docs_update_with_code` rule; it is restated here because it is central to this milestone, not optional.

**Per-doc impact in `docs/training/`:**

| Doc | Impact |
|---|---|
| `README.md` | Minor + ongoing: SHA refresh per touched doc; new architecture pointer to ADR-0001 |
| `rl-environments.md` | Minimal — envs do not access DB directly |
| `feature-catalog.md` | Minimal — no structural change |
| `reward-shaping.md` | Minor — code-path citations move |
| `agent-architecture.md` | Minor — validation/promotion reads become repository calls in citations |
| `training-data-capture.md` | **Major rewrite of "writers" and "readers" columns** — every entry becomes a repository name. Tables themselves are unchanged. |
| `memory-system.md` | **Major** — `services/memory/db.py` refactor changes the internal call graph; LLM chain unchanged but every "function does X" sentence becomes "function calls repository X" |
| `training-pipeline.md` | Moderate — internal DB calls in `scripts/train_pipeline.py` become repository calls; entry points unchanged |
| `validation-promotion.md` | Moderate — gate code paths cite repositories; gates themselves unchanged |
| `hyperparameter-tuning.md` | Minor — code-path citations |

**Outside `docs/training/`:**
- `CLAUDE.md` — new "Critical Rule: No direct DB access — business modules take repository Protocol arguments; only `*/adapters/postgres.py` files may import psycopg."
- `docs/TRAINING_RUNBOOK.md` — local-dev section adds the `pg-test` container.
- **New** `docs/adr/0001-repository-pattern.md` — captures incident history, why repositories, why raw psycopg + Protocols (not SQLAlchemy), conventions for adding a new repository, conventions for writing a Fake.
- **New** `docs/adr/0002-test-isolation.md` — captures L1 + L2 + L4 design (pg-test container, prod role split, pg_hba, rollback fixture), why each layer exists, how to add a new test that needs real PG.

**Doc-as-CI-gate (proposed):** A grep-based CI check fails if a commit touches `src/swingrl/<area>/` or `services/memory/` without also touching the relevant `docs/training/*.md`. Catches doc drift mechanically rather than relying on reviewer vigilance.

## Phase plan

Seven phases, each shippable independently, each ending with green CI on `pg-test` and updated docs in the same commits.

### Phase 19.2.0 — Foundation (BLOCKING)

Lays the safety floor and the pattern templates.

- Add `pg-test` service to `docker-compose-dev.yml` (separate volume, port, network).
- Update `scripts/ci-homelab.sh` to point `DATABASE_URL` at `pg-test:5432/swingrl_test`.
- Strengthen `tests/conftest.py` `pytest_configure` to also check hostname (defence-in-depth only — L1 is the real defence).
- Add `tests/fixtures/transactional.py` with the psycopg savepoint rollback fixture; document its DDL-escapes-rollback limit.
- Add empty `src/swingrl/ports/` package as boundary marker.
- Add `HaltRepository` as the template implementation (already-simple module, demonstrates Pg + Fake + tests + docs).
- Write `docs/adr/0001-repository-pattern.md` and `docs/adr/0002-test-isolation.md`.
- Update `CLAUDE.md` with the no-direct-DB rule (will fail audit until later phases — that's expected, the rule warns contributors).
- Update `docs/training/README.md` with architecture pointer to ADR-0001.

**Effort:** Medium. **Risk:** Low. **Dependency:** None.

### Phase 19.2.1 — Low-effort modules

Build pattern muscle on simple modules.

Modules: `scheduler/halt_check` (template promoted), `monitoring/alerter`, `monitoring/stuck_agent`, `data/validation`, `data/verification`, `execution/adapters/binance_sim`, `execution/pipeline` (halt read only).

Each module gets Protocol + PgRepository + FakeRepository + refactored business module + rewritten unit tests + a small set of integration tests against `pg-test` + same-commit doc updates for any citations in `docs/training/*.md`.

**Effort:** Low per module × ~7 modules = Medium overall. **Risk:** Low. **Dependency:** 19.2.0.

### Phase 19.2.2 — Medium-effort modules

The bulk of the data, feature, reporting surface.

Modules: 6 data ingestors, `data/gap_fill`, `data/base`, `features/{macro, fundamentals, hmm_regime, pipeline}`, `training/data_loader`, `reporting/iteration_report`, `shadow/{promoter, shadow_runner}`, `monitoring/wash_sale`, `dashboard/pages`.

Repositories grouped by aggregate rather than by file. DataFrame-returning reads stay DataFrame-returning. Fakes for bulk-data repositories accept seed DataFrames at construction.

Heavy doc work this phase: `training-data-capture.md` rewrite is the major piece; `validation-promotion.md` and `training-pipeline.md` get moderate updates; README SHA refresh.

**Effort:** High. **Risk:** Medium — `training/data_loader` is on the hot path; benchmark before/after to catch perf regression. **Dependency:** 19.2.0.

### Phase 19.2.3 — High-effort modules (execution + risk)

The modules where bugs cost real money.

Modules: `execution/fill_processor`, `execution/risk/position_tracker`, `execution/reconciliation`, `execution/risk/risk_manager`, `execution/risk/circuit_breaker`, `agents/backtest`.

Repositories: `TradeRepository`, `PositionRepository` (cost basis, P&L), `CircuitBreakerRepository`, `RiskPolicyRepository`, `BacktestResultsRepository`.

Idempotency tests that exercise `ON CONFLICT DO UPDATE SET` (fills, backtest re-runs) stay as integration tests against `pg-test`. Fakes here would lie about SQL semantics; the whole point of these tests is to verify the SQL.

Per-test rollback for these integration tests; truncate-and-reseed for the handful that need DDL behaviour.

`agents/backtest` already takes `db: Optional[DatabaseManager]`; refactor preserves the `None` path (offline backtest with no persistence).

**Effort:** High. **Risk:** High — live-trading code. Mitigated by strict TDD on every change, paper-trading verification before merge, no merge during market hours, documented recovery checklist. **Dependency:** 19.2.0, 19.2.1 (pattern proven).

### Phase 19.2.4 — Memory subsystem refactor

The very-high-effort modules — code that currently bypasses `DatabaseManager` with direct `psycopg.connect()` calls, plus the 40KB SQL block in `services/memory`.

First: convert `meta_orchestrator` and `epoch_callback` to route through `DatabaseManager` (no functional change; mandatory for repository pattern to apply).

Then: introduce `MemoryRepository`, `ConsolidationRepository`, `EpochMemoryRepository`, `RewardAdjustmentRepository`, `TrainingRunRepository`. CTEs in `services/memory/db.py` consolidation queries become methods on the repository — SQL unchanged, just behind a typed interface. JSONB ops stay in PgRepository; FakeRepository uses Python dict equivalents.

The `consolidate.py:1436` NoneType bug (the streaming refactor's log line that does `len(memories)` on a path where `memories` is `None`) is fixed in passing during this phase.

`memory-system.md` major rewrite. The `tests/test_memory_service.py` suite (~3300 lines) splits into unit-tier (against fakes) and integration-tier (against pg-test) files.

**Effort:** Very High. **Risk:** Medium — memory service is async-heavy but not on the live-trading critical path. **Dependency:** 19.2.0, 19.2.2.

### Phase 19.2.5 — Production server-side hardening

Apply Travis CI's #1 lesson. Done during a planned maintenance window (weekend or pre-market).

- Pre-flight audit: grep `src/swingrl/` and `services/memory/` for any code that issues `TRUNCATE`, `DELETE` without `WHERE`, or `DROP` on prod tables. None should exist by this phase — but verify.
- Migration: introduce `swingrl_admin` role that owns schema and runs DDL. `swingrl` role keeps DML on application tables; loses `TRUNCATE` and `DROP`; loses `DELETE` on audit tables.
- Update `services/memory/migrations/` runner and `db/migrate.py` to authenticate as `swingrl_admin`.
- `pg_hba.conf` rules: prod `swingrl` database accepts connections only from the prod app container subnet; reject all others.
- Rollback procedure documented and tested in a non-prod restore beforehand.
- `docs/adr/0002-test-isolation.md` updated with the implemented config.

**Acceptance:** from a dev laptop, `psql postgresql://swingrl:...@pg16:5432/swingrl` returns `connection refused` (pg_hba) or auth-rejected. Production trading runs uninterrupted across the window.

**Effort:** Medium. **Risk:** High — touches live trading DB. Mitigated by maintenance window, pre-flight audit, tested rollback. **Dependency:** 19.2.1 through 19.2.4 complete.

### Phase 19.2.6 — Phase 19.1 reintegration

Land the paused Phase 19.1 work on top of the new foundation.

- Rebase Phase 19.1 branch onto post-19.2.5 main.
- Confirm `consolidate.py:1436` is fixed (likely already from 19.2.4).
- Rewrite the 50 currently-failing tests to use fakes or `pg-test` rollback fixture.
- Re-run full CI on pg-test. Open PR to main.
- Update `.planning/ROADMAP.md`: 19.2 milestone closeout, 19.1 landed.

**Effort:** Medium. **Risk:** Low. **Dependency:** 19.2.0 through 19.2.5.

## Cross-phase invariants

- Every phase ends with green CI on `pg-test`. The string `pg16` does not appear in `scripts/ci-homelab.sh` after 19.2.0 except as a target for the hardening migration in 19.2.5.
- Every code change in a phase that touches material documented in `docs/training/*.md` updates those docs in the same commit. The README SHA is refreshed in the merge commit.
- Every phase that introduces a new repository adds a listing to `docs/adr/0001-repository-pattern.md`.
- No phase merges during US-market hours.
- Strict TDD for execution/* code (Phase 19.2.3).
- No phase uses `git push --force` against `main`. Branches are rebased and force-pushed only within the feature branch.

## Open questions for implementation phase

1. **Repository granularity:** one repository per aggregate or one per table? Default to per-aggregate (PositionRepository covers `positions` + `portfolio_snapshots` + `high_water_mark`), but call this out at planning time per module.
2. **Async repositories:** `services/memory` is async; PgRepositories there will use `psycopg.AsyncConnection`. Fakes can stay sync; tests use `pytest-asyncio` as today.
3. **Migration role implementation:** is the right shape a separate Postgres user, a separate role granted to the same user, or a separate database connection string used only by the migration runner? Phase 19.2.5 plan resolves this with concrete config.
4. **Doc-as-CI-gate enforcement granularity:** path-prefix matching is fragile (`src/swingrl/data/` touching is hardly a `training/feature-catalog.md` matter every time). The implementation phase should propose a precise mapping rather than a blunt rule.
