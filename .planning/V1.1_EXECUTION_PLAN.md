## Why this plan exists (situation as of 2026-06-05 ET)

Three facts forced a re-sequencing of the back half of v1.1:

1. **The work branch is 249 commits ahead of `main`, and `main` is a strict ancestor**
   (zero divergence — clean linear history). `main` predates the Postgres migration;
   everything since early April (Postgres migration, memory infra, CPS framework,
   `docs/training/` reference set, the 19.2 spec) lives only on
   `gsd/phase-19.1-memory-agent-infrastructure-and-training`. That unmerged delta is a
   standing integration risk.

2. **The 19.1 PR cannot merge.** Local tests pass (`975 passed / 391 skipped / 0 failed`)
   only because `DATABASE_URL` is unset and live-DB tests skip. On homelab CI, where
   `DATABASE_URL` points at the shared `pg16`, ~50 tests fail from inter-test state
   pollution — and the test approach has destroyed production data multiple times.

3. **Memory is empirically *hurting* training.** Across iter 3–4, control folds (no LLM
   advice) beat treatment folds by **2.7–5.1× CPS**. The Phase 1 prompt+reward refocus
   (handoff Group C) is empirically mandatory; deferring it has real cost.

The 19.2 spec (2026-05-19) correctly diagnoses #2 and designs a four-layer defence, but
sequences the empirically-mandatory training fix (#3) *last* (19.2.6), behind a 7-phase,
36-module repository refactor. **This plan re-sequences:** build the minimal safety floor,
ship the training value and drain the 249-commit delta, *then* do the full architectural
hardening — instead of blocking the urgent fix behind the large refactor.

## Branch strategy

- **Old convention `gsd/…` is retired** (GSD tooling no longer in use). The existing
  `gsd/phase-19.1-memory-agent-infrastructure-and-training` branch keeps its name purely
  for historical reference and serves as the **one-time consolidation vehicle**.
- **New convention: `swingrl/<N>-<slug>`** (e.g. `swingrl/19.1-training-refocus`,
  `swingrl/19.2.0-test-foundation`).
- **Consolidation flow:** finish Stage 1 *on the existing `gsd/` branch* → homelab CI green
  → open one consolidation PR → **`--no-ff` merge to `main` preserving all 249 commits**
  (retains Postgres-migration and iter 0–4 recovery forensics) → retire the branch.
- **From Stage 2 onward:** every phase gets a small, well-named `swingrl/<N>-<slug>` branch
  cut from the freshly-updated `main`. No more mega-branch.

## Gate model

Every stage passes these gates in order. Per `CLAUDE.md`, nothing is written without
G1/G2, and nothing merges without G3/G4.

| Gate | When | What happens |
|---|---|---|
| 🚩 **G1 — Spec approval** | after the stage spec is written | user reviews & approves the spec before any planning |
| 🚩 **G2 — Plan approval** | after `writing-plans` produces the plan | user reviews & approves the plan before any code |
| 🚩 **G3 — CI green** | after implementation | homelab `scripts/ci-homelab.sh` must pass before a PR is opened |
| 🚩 **G4 — Merge** | after PR opened | user merges (branch protection / self-approval) |

**Special gates (additive):**
- 🛑 **Backup gate** — any destructive production-DB operation (handoff Group A iter-5 wipe,
  Group D consolidation deletes) requires plan-mode approval **and a verified backup**
  immediately before execution.
- 🕐 **Market-hours gate** — execution/risk code (Stage 3.4) does **not** merge during US
  market hours, and requires paper-trading verification before merge.

### Stage 2.R — Training-system redesign (scoping & planning)  📝 scoping next

**Why this exists:** The Stage 2 runbook (A→E) assumed we could re-consolidate the existing memory
corpus and re-run iter-5 with refocused *prompts* and watch the harm ratio collapse. A 2026-06-11
investigation undermined both assumptions and surfaced deeper unresolved questions about the
meta-trainer itself. We pause and redesign across three workstreams. Group C's merged prompt/diagnosis
code is kept; what changes is the plan on top of it.

**Findings that triggered the pause (2026-06-11, verified against pg16 + docs):**
- **The 84 consolidations are pre-CPS.** 0/84 mention CPS/capital-preservation; 56 are Sharpe-framed,
  15 pass/win-rate. They encode the old objective we believe caused the harm.
- **The memory corpus is original surviving data, not recovered.** Spans 2026-03-26→04-06; Plan A only
  restored `iteration_results`+`backtest_results`. It's unreliable from *capture bugs* + wrong objective,
  not recovery loss.
- **"iter-5" is not cleanly selectable.** `memories` and `training_epochs` have **no iteration column**.
  De-facto selectors (memories `archived=0` ≈ 832k of 4.96M; `training_epochs` 850k all dated 04-06) are
  inferences, not a verified key. Group A's deletes can't be trusted until a selector is proven (handoff's
  own open item D2, applies to A too).
- **The meta-trainer's levers were never verified to move training in the intended direction.** Only
  evidence is the 2.7–5.1× *harm*. Group C refined guardrails (diagnosis→correction menu, fold protection,
  CPS goal block) but never proved a lever-pull produces the intended behavior change. Historical
  `reward_adjustments.outcome_sharpe` was buggy (fixed in Group C, never re-run) so past effectiveness
  can't be analyzed retrospectively either.
- **Attribution discipline discussed but never adopted.** `reward-shaping-vs-hyperparameters.md`
  (lines 128–132, 237, 256): changing reward-weights AND hyperparameters in the same iteration makes
  attribution *mathematically impossible*; it recommends **alternating one-lever-per-iteration**. The
  meta-trainer still moves both at once at runtime — so even a successful Group E wouldn't isolate *which*
  lever worked. We applied this to the C4 decision (why C4 was dropped) but never to the runtime levers.

**Governing metaphor:** the meta-trainer is a *coach* — but if he can't see the game properly, he can't
give proper advice. Information sufficiency (what the coach can observe) is as central as the levers
(what the coach can do).

**Three workstreams to scope:**

| WS | Question | Notes / references |
|---|---|---|
| **WS1 — Memory capture** | Salvage the corpus or discard and start fresh? Root-cause *why* capture produced bad/incomplete data before any re-run. | Open bugs: F2 SAC cadence (688k vs ~350 — symptom fixed, **root cause never investigated**); `max_single_loss` in dollars breaks CPS v2 (**documented, not fixed**); epoch-logger PPO-only SB3 keys; thresholds firing ~80% of epochs. Lean: discard corpus, keep only iter 0–4 *results* as evidence + diagnosis baseline. |
| **WS2 — Meta-trainer levers + observability** | What *should* the levers be, how do we prove they work, and what must the coach be able to *see* to wield them? | Current levers: mid-fold reward-weight adjustment (harm source), between-iteration HP tuning, patterns→prompts.
